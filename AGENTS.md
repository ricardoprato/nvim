# AGENTS.md — Review rules for this Neovim configuration

This repository is a personal Neovim configuration written in Lua on top of
`lazy.nvim`. There is no application, no build step, no test suite and no CI.
The only "runtime" is an editor session, and the only way a defect shows up is a
broken startup, a dead keymap or a plugin that silently stops loading.

Review code against the rules below. Report a finding only when you can point at
the line that violates one of them and describe the concrete failure it causes.

## Scope

| In scope | Out of scope |
|----------|--------------|
| `init.lua`, `lua/**/*.lua`, `after/**/*.lua` | `lazy-lock.json` (generated by lazy.nvim) |
| Plugin specs, keymaps, autocmds, options, utils | `snippets/*.json`, `after/snippets/*.json` (data) |
| Lua correctness and startup safety | Style and whitespace (`stylua` owns those) |

## Non-goals — never report these

- **Missing tests.** This project has no test framework and will not get one.
  Never ask for unit tests, integration tests, mocks or coverage.
- **Formatting.** `stylua` runs on every save with a pinned `.stylua.toml`
  (tabs, width 120, `collapse_simple_statement = "Never"`). Indentation, quote
  style and line breaks are settled; do not comment on them.
- **Comment language.** The tree mixes English and Spanish comments. Both are
  accepted.
- **Plugin choice.** Which plugin is used is the author's decision, not a
  review finding. Review how it is configured, not whether it deserves to exist.
- **Version bumps** in `lazy-lock.json`.

## Principles

These are the criteria the code is judged by, in priority order.

### 1. Fail fast

Errors must surface, not disappear.

- Do not wrap a call in `pcall` unless the failure is genuinely expected and the
  fallback path is written out. A bare `pcall(require, "x")` that discards the
  error hides a broken config for weeks.
- When a required external binary or parser is missing, notify (`vim.notify`
  with `vim.log.levels.WARN`/`ERROR`) instead of returning silently.
- Never leave an empty `else` or an error branch that only `return`s with no
  explanation comment.

### 2. KISS

- Prefer the plugin's declarative `opts` table over a `config` function. Write
  `config` only when there is imperative work to do (autocmds, commands,
  catch-up loops) — and say in a comment why.
- No abstraction layers over a single call site. A helper used once is a helper
  too many unless it names something genuinely unclear.
- No metatables, no dynamic `_G` lookups, no clever string building where a
  literal table works.

### 3. YAGNI

- No configuration option set to its own default value, unless a comment
  explains that pinning it is deliberate (as `.stylua.toml` does).
- No commented-out blocks kept "for later". Git has them.
- No parameters, fields or branches that nothing in the repo reaches.

### 4. SRP — one file, one concern

- `lua/plugins/<name>.lua` configures exactly one plugin and returns its spec.
- `lua/utils/<name>.lua` returns a module table `M` with a single, nameable
  responsibility.
- `lua/config/{options,keymaps,autocmds}.lua` hold only their own kind of
  setting. A keymap defined inside `options.lua` is a finding; a plugin-specific
  keymap belongs in that plugin's `keys` table, not in `config/keymaps.lua`.

### 5. Documentation of Concerns (DoC)

Comments explain **why**, never **what**. The bar in this repo is high — see
`lua/plugins/csvview.lua` and `.stylua.toml` for the expected depth.

- Every non-obvious option needs a comment stating the tradeoff it encodes.
- Every workaround names the upstream limitation it works around.
- A comment that restates the code (`-- set the header line`) is noise; flag it.

## Neovim and lazy.nvim rules

| Rule | Why it matters |
|------|----------------|
| Never call `require("plugin")` at the top level of a spec file | It loads the plugin at startup and defeats lazy loading. Call it inside `config`, `keys` or a callback. |
| Every spec must declare a lazy trigger (`event`, `ft`, `cmd`, `keys`) or state in a comment why it loads eagerly | An untriggered spec is loaded on every startup. |
| Every keymap needs a `desc` | `which-key` is driven by it; a missing `desc` leaves a blank entry. |
| Every `nvim_create_autocmd` belongs to an augroup, and every augroup created in a `config` uses `{ clear = true }` | Without it, re-sourcing the config stacks duplicate handlers. |
| Use `_G.Config.new_autocmd` for config-level autocmds | It is the existing wrapper defined in `init.lua`; bypassing it splits the `custom-config` group. |
| `local` everything | A stray global leaks into every buffer. `_G.Config` is the only sanctioned global. |
| Prefer `vim.uv` over `vim.loop`, `vim.system` over `vim.fn.system`, `vim.o`/`vim.bo` over `vim.opt` for scalars | These are the current APIs in the Neovim version this config targets, and the rest of the tree already uses them. |
| Guard anything that assumes a filetype, buffer or window is still valid inside async callbacks | `vim.api.nvim_buf_is_loaded` / `nvim_win_is_valid` before touching it. |
| A `config = function(_, opts)` must actually pass `opts` to `setup` | Dropping it silently discards every option declared in the spec. |
| Blocking work belongs off the startup path | No synchronous shell calls, file reads or network at spec load time. |

## Review checklist

Work through this in order and stop at the first level that produces findings.

- [ ] **Breaks startup** — syntax error, missing `return`, wrong spec shape,
      call to an API that does not exist.
- [ ] **Breaks silently** — swallowed error, autocmd without `clear`, `opts`
      dropped, lazy trigger that never fires.
- [ ] **Violates a principle above** — with the line and the concrete
      consequence named.
- [ ] **Undocumented decision** — a non-obvious value with no `why`.

## Reporting

- One finding per line-level problem, with `file:line`.
- State the failure, not the preference: *"this autocmd duplicates on every
  `:source`"*, not *"consider using clear"*.
- If the diff is correct, say so plainly. Do not invent findings to fill a
  report, and do not restate the checklist back as commentary.
